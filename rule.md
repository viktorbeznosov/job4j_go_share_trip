# Правила проекта ShareTrip

## 1. Общие принципы

### 1.1. Цели проекта
Разработка учебного сервиса для организации совместных поездок (car-sharing), реализующего ключевые бизнес-процессы: создание, публикация, поиск поездок, бронирование мест, управление заявками и статусами.

### 1.2. Архитектурный стиль
Проект следует принципам **Чистой архитектуры (Clean Architecture)** и **Предметно-ориентированного проектирования (DDD)**:
- **Изоляция доменной логики**: Бизнес-сущности и правила находятся в `internal/domain/` и не зависят от фреймворков, баз данных или внешних API.
- **Направление зависимостей внутрь**: Слой `handler` зависит от `service`, `service` зависит от `repository` (интерфейса), а `repository` (реализация) зависит от инфраструктуры.
- **Тестируемость**: Использование интерфейсов для моков и изолированного тестирования бизнес-логики.

### 1.3. Технологический стек
- **Язык**: Go 1.21+
- **HTTP-фреймворк**: [Fiber](https://gofiber.io/) v2.x
- **База данных**: PostgreSQL
- **Драйвер БД**: `pgx` v5.x
- **Аутентификация**: Keycloak (JWT)
- **Логирование**: `log/slog`
- **Метрики**: Prometheus
- **Трассировка**: OpenTelemetry + Jaeger
- **Миграции**: `golang-migrate/migrate`


### 2.2. Принципы организации кода в `internal/`
- Каждый домен (агрегат) выделяется в отдельную директорию внутри `domain/`.
- Внутри директории домена соблюдается разделение на слои:
  - `entity/` — бизнес-сущности, инварианты, конструкторы.
  - `repository/` — интерфейс для хранения и его реализация.
  - `service/` — бизнес-логика, координация репозиториев.
  - `handler/` — HTTP-обработчики, DTO для запросов и ответов.

## 3. Стандарты кодирования

### 3.1. Форматирование и стиль
- Код должен быть отформатирован с помощью `go fmt` и `goimports`.
- Экспортируемые идентификаторы: `PascalCase`.
- Приватные идентификаторы: `camelCase`.
- Переменные: краткие и осмысленные (`ctx`, `req`, `db`, `trip`).
- Интерфейсы: с суффиксом `-er` или по названию роли (`Reader`, `Repository`).
- Константы: `PascalCase` или `UPPER_SNAKE_CASE`.

### 3.2. Обработка ошибок
- Ошибки всегда обрабатываются явно. Не использовать `_`.
- Использовать `fmt.Errorf` с `%w` для сохранения цепочки ошибок.
- В доменном слое возвращать кастомные ошибки для бизнес-ситуаций.
- В обработчиках логировать ошибки и возвращать понятный клиенту HTTP-статус.

### 3.3. Логирование
- Использовать структурированное логирование `slog`.
- Логгер должен быть обогащен контекстом (`correlation_id`, `trace_id`, `handler`, `trip_id`).
- Получать логгер из контекста через `logctx.Logger(ctx)`.
- Не логировать пароли, токены и другие чувствительные данные.

### 3.4. Контекст
- `context.Context` передается первым аргументом во все функции, которые работают с запросами, БД или внешними системами.
- В Fiber-обработчиках использовать `c.UserContext()` для доступа к контексту.

## 4. Доменная модель и бизнес-процессы

### 4.1. Агрегаты и сущности
- **Trip (Поездка)** — центральный агрегат. Содержит информацию о маршруте, времени, водителе, количестве мест и статусе.
- **Slot (Место)** — часть агрегата Trip, управляет доступными местами. Статусы: `AVAILABLE`, `BOOKED`, `CANCELLED`.
- **TripIssue (Заявка)** — сущность, представляющая заявку пассажира на участие в поездке.

### 4.2. Жизненный цикл поездки (статусы)

- **Draft**: черновик, создан водителем.
- **Published**: опубликована, доступна для заявок.
- **Matched**: есть принятая заявка.
- **Confirmed**: подтверждена водителем и пассажиром.
- **InProgress**: поездка началась.
- **Finished**: завершена.
- **Cancelled**: отменена.

### 4.3. Бизнес-правила
1.  **Лимит активных заявок**: Пассажир не может иметь более N активных заявок одновременно.
2.  **Срок жизни заявки**: Заявка автоматически отменяется по истечении времени.
3.  **Двустороннее подтверждение**: Переход в `Confirmed` возможен только после подтверждения обеими сторонами.
4.  **Ограничение вместимости**: Нельзя забронировать мест больше, чем указано в поездке.
5.  **Права доступа**: Только водитель может изменять статусы и редактировать поездку.

### 4.4. Доменные события
Использовать Outbox-паттерн (`internal/shared/outbox/`) для надежной публикации событий:
- `TripCreated`
- `TripPublished`
- `TripIssueSubmitted`
- `SlotBooked`
- `TripCancelled`

## 5. API и HTTP-слой

### 5.1. Роутинг
- Все маршруты группируются в `internal/api/route.go`.
- Группа `/trip` для всех операций с поездками.
- Публичные эндпоинты (например, `/ready`, `/metrics`) не требуют аутентификации.

### 5.2. Мидлвары
Порядок применения в `main.go`:
1.  `Correlation` — добавление/проксирование `correlation-id`.
2.  `HTTPMetrics` — сбор метрик по запросам.
3.  `KeycloakRefreshTokenMiddleware` — проверка JWT-токена.
4.  `RequireClientRole` — проверка роли для защищенных маршрутов.

### 5.3. DTO (Request / Response)
- Запросы: `internal/domain/{domain}/handler/request/`.
- Ответы: `internal/domain/{domain}/handler/response/`.
- Каждый DTO запроса должен иметь метод `Validate() error`.
- Поля DTO должны быть аннотированы тегами `json`.
- В ответах использовать структуры `SuccessResponse`, `ErrorResponse` для единообразия.

## 6. Работа с данными

### 6.1. Миграции
- Файлы в `migrations/` с форматом: `{timestamp}_{description}.sql`.
- Использовать `golang-migrate` для применения миграций.

### 6.2. Репозитории
- Интерфейс репозитория определяется в пакете `repository/`.
- Реализация для PostgreSQL находится там же.
- Использовать `pgxpool.Pool` для работы с БД.
- Для сложных операций использовать паттерн `UnitOfWork`.

### 6.3. Транзакции
- Критически важные операции (изменение нескольких агрегатов) должны выполняться в транзакциях.
- Использовать `pgx.Tx` и шаблон `defer tx.Rollback()`.

## 7. Наблюдаемость (Observability)

### 7.1. Логирование
- Уровни: `Debug`, `Info`, `Warn`, `Error`.
- Логировать каждый HTTP-запрос с `method`, `path`, `status`, `duration`.
- Логировать ошибки с полным контекстом.

### 7.2. Метрики (Prometheus)
- Автоматический сбор HTTP-метрик через мидлвар.
- Добавлять бизнес-метрики по необходимости (`trip_created_total`, `trip_published_total`).
- Эндпоинт для метрик: `/metrics`.

### 7.3. Трассировка (OpenTelemetry)
- Инициализация провайдера в `main.go` с настройкой экспортера в Jaeger/OTLP.
- Создавать спаны для каждого HTTP-запроса и для ключевых операций в сервисах.
- Добавлять атрибуты: `trip_id`, `client_id`, `status`.
- Добавлять заголовок `trace-id` в HTTP-ответ.

## 8. Тестирование

### 8.1. Виды тестов
- **Юнит-тесты**: Рядом с кодом, `*_test.go`. Проверка изолированных функций и структур.
- **Интеграционные тесты**: В `internal/api_test/`, с суффиксом `_integration_test.go`. Проверка сценариев с реальной БД и HTTP-клиентом.

### 8.2. Инструменты
- `test_utils` для генерации тестовых данных и токенов.
- Для интеграционных тестов рекомендуется поднимать тестовую БД в контейнере (`testcontainers`).

### 8.3. Запуск
Использовать команды из `Makefile`:
- `make test` — все тесты.
- `make test-integration` — интеграционные тесты.
- `make coverage` — отчет о покрытии.

## 9. Аутентификация и авторизация

### 9.1. Keycloak
- Проверка JWT-токенов через `middleware.KeycloakRefreshTokenMiddleware`.
- Валидация ролей через `middleware.RequireClientRole`.

### 9.2. Получение данных пользователя
- Информация о пользователе извлекается **ТОЛЬКО** из валидированных JWT-claims.
- Использовать `middleware.ClaimsFromContext(c)` для получения `ClientCredentials`.
- Не доверять `client_id` из тела запроса.

## 10. Сборка, развертывание и окружение

### 10.1. Makefile
- `make run` — запуск приложения.
- `make build` — сборка бинарного файла.
- `make test` — запуск всех тестов.
- `make migrate-up` / `make migrate-down` — управление миграциями.
