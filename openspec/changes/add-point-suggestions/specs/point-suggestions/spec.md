# Spec Delta

## Purpose

Подсказка пунктов маршрута: выдаёт существующие `from`/`to`-пункты поездок и заявок с подстрочным поиском без учёта регистра, чтобы пользователь выбирал название из списка, а не вводил его вручную с риском расхождений в фильтрах.

## ADDED Requirements

### Requirement: Endpoint подсказки пунктов отдаёт совпадения по подстроке
Система SHALL предоставлять защищённый endpoint, принимающий параметр `term` и возвращающий до 10 пунктов, в которых `term` встречается как подстрока без учёта регистра.

#### Scenario: Нижний регистр в запросе находит запись в верхнем
- **WHEN** аутентифицированный пользователь запрашивает `GET /points?term=мос`, а в базе есть пункт `Москва`
- **THEN** ответ `200` со статусом `Success` и `data.items` содержит `Москва`

#### Scenario: Верхний регистр в запросе находит запись в нижнем
- **WHEN** аутентифицированный пользователь запрашивает `GET /points?term=МОС`, а в базе есть пункт `москва`
- **THEN** ответ `200` и `data.items` содержит `москва`

#### Scenario: Одна буква находит несколько городов
- **WHEN** в базе есть `Иркутск` и `Ижевск`, а пользователь запрашивает `GET /points?term=И`
- **THEN** ответ `200` и `data.items` содержит оба пункта

#### Scenario: Нет совпадений
- **WHEN** пользователь запрашивает `GET /points?term=какойтогородкоторогонет`
- **THEN** ответ `200` со статусом `Success` и пустым `data.items`

### Requirement: Подсказка охватывает пункты поездок и заявок, откуда и куда
Система SHALL собирать пункты из колонок `from_point` и `to_point` обеих таблиц поездок и заявок.

#### Scenario: Пункт только из поездки попадает в подсказку
- **WHEN** существует поездка с `from_point = Тверь`, других записей с таким пунктом нет
- **THEN** запрос `GET /points?term=твер` включает `Тверь` в `data.items`

#### Scenario: Пункт только из заявки попадает в подсказку
- **WHEN** существует заявка с `to_point = Калуга`, других записей с таким пунктом нет
- **THEN** запрос `GET /points?term=калуг` включает `Калуга` в `data.items`

### Requirement: Подсказка не фильтрует по статусу и видимости
Система SHALL включать в подсказку пункты всех записей независимо от их статуса и без фильтрации по роли или правам видимости зрителя.

#### Scenario: Пункт отменённой поездки доступен в подсказке
- **WHEN** единственная поездка с пунктом `Самара` имеет статус `canceled`
- **THEN** запрос `GET /points?term=самар` включает `Самара` в `data.items`

#### Scenario: Пункт черновика заявки доступен в подсказке
- **WHEN** единственная заявка с пунктом `Рязань` имеет статус `draft`
- **THEN** запрос `GET /points?term=рязан` включает `Рязань` в `data.items`

### Requirement: Пункты дедуплицируются
Система SHALL возвращать каждый уникальный пункт не более одного раза при любом количестве записей с этим пунктом.

#### Scenario: Повторяющийся пункт выдаётся один раз
- **WHEN** в трёх поездках указан `from_point = Москва`, а в одной заявке `to_point = Москва`
- **THEN** `data.items` содержит `Москва` ровно один раз

### Requirement: Подсказка ограничена десятью пунктами
Система SHALL возвращать не более 10 пунктов на один запрос.

#### Scenario: Больше десяти совпадений
- **WHEN** под строку подстроки подходят 25 различных пунктов
- **THEN** `data.items` содержит ровно 10 элементов

#### Scenario: Меньше десяти совпадений
- **WHEN** под строку подстроки подходят 3 различных пункта
- **THEN** `data.items` содержит 3 элемента

### Requirement: Пустой или отсутствующий term отдаёт начало словаря
Система SHALL трактовать отсутствующий или пустой `term` как запрос без фильтра и вернуть первые 10 пунктов.

#### Scenario: Без параметра term
- **WHEN** аутентифицированный пользователь запрашивает `GET /points`
- **THEN** ответ `200` и `data.items` содержит до 10 пунктов из всех записей

#### Scenario: Пустой term
- **WHEN** пользователь запрашивает `GET /points?term=`
- **THEN** ответ `200` и `data.items` содержит до 10 пунктов из всех записей

### Requirement: Порядок подсказки детерминирован
Система SHALL возвращать пункты в алфавитном порядке без учёта регистра, чтобы ответ был воспроизводимым.

#### Scenario: Детерминированный порядок
- **WHEN** подходят `Владивосток`, `Волгоград` и `Воронеж`
- **THEN** `data.items` выстроен как `Владивосток`, `Волгоград`, `Воронеж`

### Requirement: Спецсимволы в term трактуются буквально
Система SHALL обрабатывать `%` и `_` в `term` как обычные символы, а не как шаблоны подстановки.

#### Scenario: Процент в запросе не матчит всё
- **WHEN** пользователь запрашивает `GET /points?term=%`
- **THEN** `data.items` содержит только те пункты, где символ `%` реально присутствует (обычно пустой список), а не все пункты системы

#### Scenario: Подчёркивание в запросе не матчит произвольный символ
- **WHEN** пользователь запрашивает `GET /points?term=м_сква`
- **THEN** `data.items` не содержит `Москва`, так как `_` ищется буквально

### Requirement: Подсказка доступна всем аутентифицированным ролям
Система SHALL разрешать запрос подсказки всем четырём ролям (`sharetrip_driver`, `sharetrip_passenger`, `sharetrip_director`, `sharetrip_admin`) и отказывать неаутентифицированным запросам.

#### Scenario: Водитель получает подсказку
- **WHEN** запрос содержит валидный токен с правом `sharetrip_driver`
- **THEN** ответ `200`

#### Scenario: Пассажир получает подсказку
- **WHEN** запрос содержит валидный токен с правом `sharetrip_passenger`
- **THEN** ответ `200`

#### Scenario: Директор получает подсказку
- **WHEN** запрос содержит валидный токен с правом `sharetrip_director`
- **THEN** ответ `200`

#### Scenario: Админ получает подсказку
- **WHEN** запрос содержит валидный токен с правом `sharetrip_admin`
- **THEN** ответ `200`

#### Scenario: Неаутентифицированный запрос
- **WHEN** запрос не содержит валидных claims аутентификации
- **THEN** ответ `401`

#### Scenario: Токен без прав ShareTrip
- **WHEN** запрос содержит валидные claims без ни одного из прав `sharetrip_*`
- **THEN** ответ `403`
