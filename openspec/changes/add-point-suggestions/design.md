# Design

## Context

Motivation — в proposal.md. Технический фон, который определяет подход:

- Подстрочный поиск в проекте **не реализован нигде**: все существующие фильтры — точное равенство (`internal/business/trip/repository/list_trip.go:170-174` → `t.from_point = ?`). Пагинация, `count` и `WHERE`-конструктор уже есть как образец.
- `trips.from_point` / `trips.to_point` и `trip_requests.from_point` / `trip_requests.to_point` — обе `TEXT NOT NULL`. Миграция не нужна.
- Требуемый доступ (все 4 роли, 401/403) — это ровно `RequireClientRole` + `RequireAnyUserPermission(...)`, уже используемые на `GET /trip/` и `GET /request/`.
- Проверено на `postgres:16` (официальный образ, `en_US.utf8` — такой же в `deploy/docker-compose.yml` и в testcontainers): `ILIKE` корректно фолдит кириллицу в обе стороны (`'МОСКВА' ILIKE '%моск%'` = true, `lower('МОСКВА')` = `москва`). Требование регистронезависимости для русского текста выполнимо без `unaccent` и расширений.
- `%` и `_` в пользовательском `term` в ILIKE-шаблоне без экранирования матчат всё — проверено: `ILIKE '%мос%%'` матчит шире, чем литеральный `%`.

## Goals / Non-Goals

**Goals:**

- Один read-only endpoint, отдающий словарь пунктов с подстрочным поиском.
- Регистронезависимость, включая кириллицу.
- Детерминированный, ограниченный 10 штуками ответ.
- Ноль миграций, ноль новых зависимостей.

**Non-Goals:**

- Любые изменения фронтенда (`job4j_go_share_trip_front` — отдельный репозиторий со своим openspec; там нужен свой change на `mat-autocomplete`).
- Изменение существующих фильтров списков (`fromPoint`/`ToPoint` остаются точными) — **не Breaking**.
- Индекс `pg_trgm`, расширения `unaccent`, полнотекстовый поиск, опечатко-устойчивость (fuzzy).
- Фильтрация по статусам и по видимости (решено: весь словарь).
- Отдельная таблица-справочник пунктов с бэкграунд-джобом синхронизации.
- Пагинация/`offset` — подсказка всегда одна страница из 10.

## Decisions

### D1. Источник: UNION двух таблиц в запросе, а не справочник

```sql
SELECT DISTINCT point FROM (
  SELECT from_point AS point FROM trips
  UNION ALL
  SELECT to_point FROM trips
  UNION ALL
  SELECT from_point FROM trip_requests
  UNION ALL
  SELECT to_point FROM trip_requests
) all_points
WHERE ($1 = '' OR point ILIKE '%' || $2 || '%')
ORDER BY lower(point)
LIMIT 10
```

- **Альтернатива A** (отвергнута): отдельная таблица `points` + тригеры/воркер синхронизации. Плюс — индекс и быстрый поиск; минус — новая сущность, источник рассинхрона, миграции, фоновая работа. Для объёма учебного проекта (единицы/десятки тысяч строк) полный скан двух колонок дешевле, чем поддерживать третий источник истины.
- **Альтернатива B** (отвергнута): CTE с частотным ранжированием (`count(*) GROUP BY`) — «частые сверху» интуитивно приятнее, но алфавитный порядок детерминирован и проще проверять в тестах.
- `DISTINCT` закрывает требование дедупликации; `lower(point)` в `ORDER BY` даёт стабильный алфавитный порядок и для кириллицы (проверено).

### D2. Экранирование спецсимволов на стороне Go, не SQL

`%`, `_` и сам `\` экранируются в `term` перед подстановкой, литерал `\` в ILIKE-шаблоне. Проще и нагляднее, чем `ESCAPE`-клауза в динамическом SQL. Побочный эффект: экранированное значение подставляется параметром (`$2`), SQL-инъекция исключена любым способом — используется только параметризованный запрос (паттерн проекта).

### D3. Точка вставки: существующий `TripRepository`, не новый слой

Метод `SuggestPoints(ctx, term)` в `internal/business/trip/repository/` рядом с `list_trip.go`: обе таблицы читает один и тот же пул (`pgxpool`), доступ уже есть. Новый слой/пакет ради одного SELECT — избыточность.

- **Альтернатива** (отвергнута): новый пакет `internal/business/points/` с entity/service/repository по образцу `trip`/`request`. Оправдано, если бы подсказка росла в домен (свой агрегат, свои правила). Сейчас это чистый read-only проектор над двумя таблицами; слой service добавил бы перенос без логики. Если capability позже вырастет — пакет выделяется без изменения контракта (спека описывает только поведение endpoint'а).

### D4. Маршрут и контракт

`GET /points?term=...` — отдельная группа уровня с `/trip`, `/request`, `/ready`, `/metrics`, а не внутри `/trip`: подсказка одинаково про обе сущности, вложенность в `trip` ввела бы в заблуждение.

Обёртка по действующему AGENTS.md — в `internal/api/response.go`:

```go
type SuggestPointsResponse struct {
    Items []string `json:"items"`
}
type SuggestPointsResponseWrapper struct {
    Status  string              `json:"status"`
    Message string              `json:"message,omitempty"`
    Data    SuggestPointsResponse `json:"data"`
    Error   string              `json:"error,omitempty"`
}
```

Так фронт получает `{status, data: {items: [...]}}` — конвенцию `ApiWrapper<T>` с его `res.data` (см. front `core/models.ts`).

### D5. Доступ: `RequireClientRole` + `RequireAnyUserPermission(все 4 правa)`

Точно повторяет `GET /trip/`. Отсутствие claims → `ClaimsFromContext` возвращает `fiber.NewError(401)`; отсутствие всех четырёх прав → `RequireAnyUserPermission` возвращает `403`. Никакого нового кода авторизации. Замечание для реализации: роль `client` (клиент Keycloak) проверяется отдельно от прав `sharetrip.*` — обе проверки нужны, как на существующих маршрутах.

### D6. Валидация

`term` необязателен; пустой = без фильтра (спека). Ограничение длины — разумный предел (256 символов) с 400 при превышении, чтобы не гонять бессмысленный запрос; ошибка переиспользует `error_mapper` (`MapValidationError`) и новую константу в `internal/api/errors/`.

### D7. Где живёт логика ограничения в 10

`LIMIT 10` в SQL, не в Go. Фильтрация в памяти после загрузки всех пунктов противоречила бы смыслу LIMIT и расходила память.

## Risks / Trade-offs

- **[`ILIKE '%x%'` не использует B-tree-индекс → полный скан**] → на объёмах учебного проекта это микросекунды; масштабирование — `pg_trgm` GIN-индекс отдельным change, когда объёмы вырастут. Деградация ограничена двумя колонками в двух таблицах.
- **Кириллический `ILIKE` зависит от колляции БД** → проверено на целевом `postgres:16` + `en_US.utf8`. Риск останется, если БД пересоздадут с колляцией `C` (lower не фолдит нелатиницу). Mitigation: интеграционный тест с кириллицей упадёт первым — это и есть страховка; в `deploy/docker-compose.yml` колляция не переопределяется.
- **`UNION ALL` без индекса растёт линейно** → см. D1; порог перехода на `pg_trgm` — зафиксирован как non-goal.
- **Словарь раскрывает пункты всех ролей** → осознанное решение (вопрос пользователю, ответ «все подряд»): названия населённых пунктов не чувствительны, а география полёта заявки — нет данных о пассажирах. Ничего персонального в ответе нет.
- **Дубль терминологии: `trip`-группа имеет `move_to_publish`, а подсказка — нет статусной логики** → не риск, напоминание: подсказка read-only, в `domain/` слой не идёт (D3).
- **`orders by lower(point)` не индексируется** → тот же трейд-оф, что и скан: жертвуем индексом ради простоты.

## Migration Plan

Миграций и конфигурационных изменений нет — только новый код + новые тесты. Деплой/откат: обычный релиз сервиса, откат = откат бинаря; новых таблиц и данных нет. Несовместимости с существующими клиентами нет — ничего не меняется, добавляется только новый маршрут.

## Open Questions

- **Частотный порядок вместо алфавитного?** Не влияет на спеку по существу (дедупликация, лимит, поиск), влияет только на `ORDER BY`. Решено в пользу алфавита (детерминизм, D1); если UX-тесты на фронте покажут, что «частые сверху» удобнее — это точечная правка D1+спека-сценария, не переворачивает design.
- **Нужен ли `count` в ответе?** Ответ — подсказка для typeahead, длина `items` сама показывает, что нашлось. Не добавляем; если фронту понадобится — поле добавляется обратно совместимо (`omitempty`).
